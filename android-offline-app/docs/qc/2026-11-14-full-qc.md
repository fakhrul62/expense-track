# EXPTRACK full quality-control audit

Date: 14 November 2026. Baseline: v1.11.0, Android code 18, published commit `0eed0837b8ff2af7ef133817759023c569c6059c`.

Follow-up: the findings below describe the original audited release. v1.11.1 remediation is documented in [the fixes report](2026-11-14-fixes.md). These fixes are included in the v1.11.3 release.

## Verdict

**Needs fixes before a clean release sign-off.** Core financial journeys work, including real Android SQLite offline storage and two-way website sync. Two reproduced sync edge cases can corrupt the displayed financial position. Eight findings are documented below: two P1, five P2 and one P3. P1 means financial correctness needs prompt attention; P2 means important remediation; P3 means a smaller usability defect. No product fixes, commits, pushes or deployments were made during this audit.

This is a broad engineering audit with executable checks, not a formal penetration test or complete WCAG certification. Passing checks establish the tested behavior, not absence of all defects.

## Findings

### QC-01 — P1: Case-insensitive category alias can turn spending into income

**Reproduced against the real sync API using an isolated test account.** A custom expense category named `income: salary` passes the case-sensitive reserved-prefix checks. Sync matches category names case-insensitively and aliases that category to the reserved Salary category. The transaction then changes direction because income is classified by category ID.

Example: a cash expense of Tk100 produces cash **-100 before sync and +100 after sync**: a Tk200 discrepancy. No unusual amount or malformed transaction is needed.

Sources: `src/lib/local-store.ts:324` (category creation), `src/lib/local-store.ts:341` (reserved categories omitted from duplicate candidates), `src/lib/sync-server.ts:22` (case-sensitive reservation), `src/lib/sync-server.ts:86` (lowercase alias lookup).

Fix: normalize reserved names consistently on client and server; prohibit aliases across income/expense classification. Add a regression covering mixed-case reserved names and audit existing aliases before designing a careful repair migration.

### QC-02 — P1: An offline repayment can survive deletion of its loan and become unmanageable

**Reproduced with the real sync API; presentation verified with the returned data in an isolated client fixture.** Device A deletes a loan. Device B later uploads a repayment created offline. The server accepts the repayment without a live principal. The Loans page shows no loan, but cash is reduced by the orphan payment. Home offers only a LOAN link for that row; the Loans page provides no parent from which to delete it.

Example: delete a Tk1,000 loan, then upload its pending Tk100 repayment. Loans visible: **0**; cash: **-100**; repayment remains stored and cannot be removed through the ordinary UI.

Sources: `src/lib/sync-server.ts:90` (category integrity without loan-parent conflict policy), `src/lib/local-store.ts:302` (deletes locally known payments), `src/lib/local-store.ts:334` (managed records reject ordinary deletion), `src/lib/loan-ledger.ts:36` (summaries start with principals), `src/app/page.tsx:385` (managed row only links to Loans).

Fix: define and enforce a transaction-aware deletion/late-payment conflict policy on the server, with explicit orphan recovery. Do not silently discard an actual repayment: retain a recoverable record or a clear conflict that the user can resolve. Cover both upload orders, repeat delivery and account isolation.

### QC-04 — P2: Delete confirmation does not contain initial keyboard focus

The delete dialog opens with focus outside it. The first Tab can still focus background content. The modal hook only wraps focus when it is already on the first or last dialog control; the delete dialog has no initial focus management.

Sources: `src/lib/use-modal.ts:11`, `src/components/DeleteConfirmModal.tsx`. Fix: focus the safe Cancel action on opening, handle focus arriving from outside, make background controls inert, and restore the trigger on closing. Retest keyboard and screen-reader behavior.

### QC-05 — P2: Small interface text fails sampled contrast targets

Computed rendered contrast included opacity and background composition. Representative failures against 4.5:1 for normal text:

| Appearance | Representative text | Contrast |
| --- | --- | --- |
| Studio | small report net/caption labels | 3.99:1 |
| Paper | small report headings/range/count; captions | 3.97:1; 3.62:1 |
| Garden | small report headings/range/count; captions | 3.90:1; 3.56:1 |
| Retro | white text on orange active Monthly / ADD controls | 3.56:1 |

Sampled Ink report labels passed. The previously fixed large monthly amount passed; this finding concerns smaller labels and controls. Fix muted text opacity/colors and orange-button foreground contrast across presets and both light/dark modes. This was targeted sampling, not a full accessibility certification.

### QC-06 — P3: Note input advertises a limit storage cannot accept

Expense notes permit 500 characters, but the serialized note plus payment-source metadata must fit in 500. A 500-character plain note passes the raw input limit and is rejected on save. Escaped characters further reduce capacity. No partial batch write or data loss was observed.

Sources: `src/components/ExpenseModal.tsx:110`, `src/lib/wallet.ts:15`. Fix: validate serialized length consistently and show a useful remaining limit/error before Save.

### QC-07 — P2: CSV formula protection misses leading control whitespace in legacy data

A legacy/API-supplied note beginning with a tab followed by `=1+1` is exported without neutralization. The current form trims notes, so this was **not reproduced through normal current note entry**. Risk applies to untrusted/legacy stored data opened in a spreadsheet.

Source: `src/lib/reports.ts:55`. Fix: check leading whitespace/control characters before formula prefixes, preserve numeric cells appropriately, and test exported files with spreadsheet applications.

### QC-08 — P2: Loan summaries scale quadratically

`src/lib/loan-ledger.ts:39` scans/parses the full entry array for every loan. Desktop measurements on this machine:

| Loans / total records | Summary time |
| --- | --- |
| 100 / 200 | 49.5 ms |
| 500 / 1,000 | 948 ms |
| 1,000 / 2,000 | 1,785 ms |

These are desktop measurements, not phone timing or a production load test. For comparison, a normal 10,000-record report calculated in 29.6 ms; CSV generation took 110.7 ms. Fix summaries with one-pass payment grouping keyed by loan ID/direction. Full-history sync every polling cycle also deserves a growth review; no destructive production load test was run.

## Remaining limits and recommended order

1. Fix QC-01 and QC-02, with both local-store and real server conflict regression coverage, before calling financial correctness complete.
2. Patch dependencies, modal focus and contrast; harden CSV and improve loan grouping.
3. Resolve the note limit and put reproducible financial/auth/sync tests into CI.
4. Complete real Google account sign-in, accepted installer upgrade/data preservation, minimum-API/physical OEM checks and scheduled reminder soak testing on a stable device.

Only API35 AOSP was exercised this turn; compile/sign minimum API24 does not prove runtime behavior on every supported phone. Backup/restore of Atlas and signing keys was not verified. Password reset, self-service account deletion and bank/cash transfer are product opportunities, not newly reproduced regressions. Transfers should avoid inventing income/expense if added later.
